Verify your download

Downloads come from GitHub releases. These checks tell you that a file was built by the project's workflows and was not changed afterwards.

There is no release yet, so there is nothing to verify today. The steps describe how it is set up; file names are examples.

1. Download from the release page only

Use the links in the download section or the GitHub releases page. Do not use copies from other sites.

2. Check the build attestation

The release workflow is written to attach a GitHub build attestation to every file: a signed statement of which workflow and which commit built it. It has not run yet, so this has not been tested on a real release. With the GitHub CLI installed:

gh attestation verify KoG-Client-linux.tar.xz -R KoG-teeworlds/kog-client

It prints the workflow and commit when the file matches, and fails if the file was changed. Use the name of the file you downloaded. This tells you where a file came from. It does not tell you that the source code is good.

3. Check the signed update manifest (advanced)

The in-app updater trusts only an Ed25519 public key that is compiled into the client. You can check the same signature by hand. You need the project's public key (it will be published in the kog-client-updates repository once the signing key has been generated), the manifest and its signature:

curl -O https://client.kog.tw/update.json
curl -O https://client.kog.tw/update.json.sig

# build the small verifier from the kog-client sources
cc -O2 -o kogsign scripts/kog/kogsign.c \
  src/engine/external/monocypher/monocypher.c \
  src/engine/external/monocypher/monocypher-ed25519.c \
  -Isrc/engine/external/monocypher

./kogsign verify "$(cat keys/primary.pub)" update.json update.json.sig

These are the commands the signing job runs itself. A valid signature means the file list and hashes in the manifest come from the project: someone who takes over the website, the domain or the GitHub Pages branch cannot make a valid manifest.

The manifest lists the files the in-app updater downloads, not the zip, tar and dmg packages. For packages, use step 2.

4. Compare file hashes

The download section shows a SHA-256 for each file the updater downloads, read from the signed manifest. Compare it with:

  • Linux: sha256sum FILE
  • macOS: shasum -a 256 FILE
  • Windows PowerShell: Get-FileHash FILE

Those hashes belong to the client program and data files used by the updater, not to the packages.

Two signatures Planned

Today a manifest carries one signature, made by the project's signing key. The signing job is set up to need the maintainer's approval in GitHub. The plan is a second signature, made with a hardware key that only the maintainer holds. The client will then require both, so neither a stolen GitHub account nor a stolen CI secret alone can publish a malicious update. A script that checks everything in one go is planned too.

If a check fails

Do not run the file. Tell us in an issue, or privately through vulnerability reporting if you think it is an attack.
