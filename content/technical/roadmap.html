Integrity checks: what they can never prove

A possible later feature is a statement about the client build, such as its hash compared with a list of known builds. It is useful to the extent that it detects an accidental or careless mismatch: an old build, a repackaged download, a withdrawn version.

Warning. No such statement proves that a client is unmodified. The program that makes the statement runs on a computer controlled by the player. Someone who modifies the client can modify the part that makes the statement, or answer with a statement copied from an honest client. Hardware-backed keys prove that a particular key exists in a particular device, not what code is using it. The statement would be a tripwire for mistakes, never a guarantee against cheating, and the client will not be described as secure against its own user.

The device key of the login has the same limit: it shows an account holder's key was used, not that the client was honest.

History

There is no stable release yet. Testing builds are on the GitHub releases page.

November 2026, before the first release

  • Forked from TClient 10.9.0 (DDNet 20.1).
  • Added a notice, a README, contributor files and issue templates.
  • Removed the ChaiScript scripting engine, chat translation and the committed Steam library, and stopped contacting TClient's servers.
  • Added the KoG version identity, an updater that verifies signed manifests, and the browser login.
  • Added release signing and upstream sync scripts, and build, release, spelling and security-scan workflows.
  • Published the first canary builds.
  • Made this documentation, with diagrams and a page per topic.
