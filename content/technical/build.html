The commands below are the ones the project's own build workflow uses. A build you make yourself is not on any channel and is not signed.

What was run. The commands below were taken from the repository's build workflows (.github/workflows/kog-build.yml, kog-package.yml) and README, where they run on GitHub's Linux, macOS and Windows runners. They were not run by hand for this page. For the dependencies and the many options, see docs/BUILDING.md, which is the DDNet guide.

Get the source

Bundled libraries come from a git submodule (ddnet-libs), which Windows and macOS builds need.

git clone https://github.com/KoG-teeworlds/kog-client
cd kog-client
git submodule update --init --recursive

Linux

The dependencies the workflow installs on Ubuntu (other distributions have the same libraries under other names):

sudo apt-get install -y cmake glslang-tools libavcodec-dev libavformat-dev libavutil-dev libcurl4-openssl-dev libfreetype6-dev libglew-dev libnotify-dev libogg-dev libopus-dev libopusfile-dev libpng-dev libsdl2-dev libsqlite3-dev libssl-dev libswresample-dev libswscale-dev libvulkan-dev libwavpack-dev libx264-dev ninja-build pkg-config spirv-tools zlib1g-dev

The client only, without server and tools, which is how the release workflows build it:

mkdir build
cd build
cmake .. -DCLIENT=ON -DSERVER=OFF -DTOOLS=OFF -DCMAKE_BUILD_TYPE=Release
cmake --build . --target game-client

macOS

brew install ffmpeg molten-vk ninja pkg-config sdl2

Then the same mkdir build, cmake and cmake --build commands as on Linux. The workflow adds -G Ninja and -DIPO=ON for release builds.

Windows

The workflow uses a Visual Studio generator for x64 and the bundled libraries. In a developer PowerShell, from the build folder:

cmake .. -A x64 -DCLIENT=ON -DSERVER=OFF -DTOOLS=OFF
cmake --build . --config Release --target game-client

Options that matter

OptionDefaultMeaning
-DAUTOUPDATE=ONOFFCompiles the updater. A release build with it fails while a channel's keys are placeholders (override: -DKOG_ALLOW_PLACEHOLDER_KEY=ON). The release workflow turns it on.
-DKOG_CHANNEL=stable|canary|devstableThe channel of this build. Canary and dev builds also need -DKOG_BUILD_NUMBER=<number> and have cl_kog_login on by default.
-DDOWNLOAD_GTEST=ONOFFDownloads GTest for the tests, if it is not installed.
-DDEV=ONOFFFaster development build, Debug by default; no packaging files.

Without -DAUTOUPDATE=ON your build has no updater at all: AUTOUPDATE is OFF by default in the CMakeLists.txt of this repository. It is ON in the package workflow, which builds the canary, dev and release packages, and not in the pull request and main CI builds.

Tests

Configure with the GTest option once, then run the test target:

cmake .. -DDOWNLOAD_GTEST=ON
cmake --build . --target run_tests

The KoG-specific tests are src/test/kog_update_test.cpp (manifest rules and signatures), kog_failsafe_test.cpp (rollback) and kog_login_test.cpp (PKCE, callback, challenge). Linux builds in CI also start the client under a virtual display for 25 seconds (scripts/kog/smoke_test.sh); the Windows and macOS runners have no GPU, so only compilation and unit tests run there.

Reproducibility

The builds are not reproducible yet. The repository has no documented procedure that rebuilds a release byte for byte, and this has not been tested. What exists instead: public workflows build the files on GitHub, every file carries a build attestation, releases are immutable, and the signing check verifies attestation, hashes and that the commit is on main before it signs. That shows where a file came from, not that two builds from one commit give identical files.

Other targets inherited from DDNet (Android, iOS, WebAssembly) have guides in the repository, but the KoG client is only built and released for Windows, macOS and Linux, and nothing about the others is checked here.
