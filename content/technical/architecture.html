Server-side programs are out of scope: this documentation describes the client.

Overview

The KoG client is the DDNet and TClient game client plus a small set of additions in separate kog_* files. The additions do two things: they keep the client up to date from a signed manifest, and they let you log in to your KoG account through your browser. Everything else is the code of the game client that the fork is based on.

Outside your computer the client talks to exactly three places that belong to KoG or its tooling, plus the game servers you choose to join and the server list inherited from DDNet:

  • client.kog.tw: signed update manifests (static files).
  • github.com: the release files that a manifest points to.
  • The KoG account service at https://kog.tw: the login, seen from the client as an OAuth 2.0 / OpenID Connect provider. The client knows its public endpoints and nothing else about it.

Design rules that follow from this layout

  • Checks are separate from effects. The rules that decide whether a manifest or a callback is acceptable live in engine/shared and are covered by unit tests (src/test/kog_update_test.cpp, kog_login_test.cpp, kog_failsafe_test.cpp). The updater and the login component only do the I/O.
  • Trust does not depend on the network path. A manifest is accepted because of its signature, not because of the host or TLS. See the update channel.
  • Nothing changes on the game connection yet. The client defines no new network message; the planned ones are described below.
  • Nothing secret leaves the machine. The device private key is made on your computer and stays in the key store. See login.

What the client adds to the game connection

The KoG client plays on any DDNet or Teeworlds server, and a KoG server can be joined by any DDNet client. This is what the KoG client adds on top of the game connection. Today that is nothing; what is planned is described from the client's side.

What is built

As built, the KoG client defines no new network message types: its protocol definition (datasrc/network.py) has no KoG entry, and the client sends no KoG message. What exists in the source is preparation:

  • src/engine/shared/kog_protocol.h reserves a message name for the hello (kog-client-hello@kog.tw) and a few capability flags. The header says it holds names only: "the messages are registered together with their handlers".
  • The client announces no capability: CKogHello::Capabilities() returns KOG_CAP_NONE.
  • The console command kog_version prints the client name, version and what it is based on. It is local.
  • The settings kog_hello and kog_telemetry exist, are off, and say "not implemented yet".
  • The version string the client sends when joining a server names this client instead of TClient, as any DDNet client sends one.

The compatibility rule (a design rule, not a test). A client feature must not change what is sent on the wire to servers that do not know about it. Stock DDNet servers and clients keep working unchanged.
