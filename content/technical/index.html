What it is and is not

The KoG client is a reference implementation: a working example of features that need both a client and a server. It is a fork of TClient 10.9.0, which is a fork of the DDNet client 20.1. The KoG-specific code lives in separate files (kog_*), so upstream changes can still be merged.

  • Added: a verifying updater, a browser login with a device key, release signing and sync scripts, build and release workflows.
  • Removed from TClient: the ChaiScript scripting engine, chat translation (it sent chat to a third-party service) and a committed Steam library. The client no longer contacts TClient's servers.
  • Not an official release of Teeworlds, DDNet or TClient, and not endorsed by their authors. "KoG Client" is a placeholder name.
  • Not required to play on KoG, and not a stable product: there is no stable release yet.
  • The executable is KoG-Client (KoG-Client.exe, KoG-Client.app). Its data folder is separate from DDNet's: %APPDATA%\KoG-Client, ~/Library/Application Support/KoG-Client, ~/.local/share/kog-client.

Canary and dev versions carry the channel (0.1.0-canary.8) and are GitHub prereleases; the last 10 of each are kept. The channel is chosen with kog_update_channel or in the settings, never from the network. Switching to a channel with an older version asks for confirmation. Source: UPDATE_CHANNEL.md.

The signed update manifest

update.json is JSON, format 2. Unknown fields are ignored by the client but are covered by the signature.

FieldMeaning
format, channel, versionRequired. The channel inside the signed text must equal the channel the client asked for.
sequenceRequired. Rises with every manifest of a channel. A client refuses one that is not higher than the last it applied.
issued, expiresRequired, Unix seconds. An expired manifest, or one from the future, is refused. The window is at most the channel's maximum.
platforms.linux-x86_64, platforms.win64The client binary: sha256, size, url.
files[], remove[]Data files to update (path below data/, hash, size, URL, optional mirrors) and data paths to delete. Executables never go through files.
packages[]Optional: name, hash, size and URL of the zip, dmg and tar.xz that this download page shows. The updater ignores it.
rollout_percent, halted, min_versionOptional: staged rollout (the bucket is a random per-install value that is never sent anywhere), withdrawal of the update, and a blocking "update required" dialog for older clients.
notes_url, changes[]Optional: release notes link (only client.kog.tw or github.com/KoG-teeworlds) and up to 3 plain-text lines.

Signature file and key ids

update.json.sig is one line: kog-update-sig-v1 KEYID SIGNATURE. The signature is Ed25519 over the exact bytes of update.json, 128 hex characters. The key id is the first 8 hex characters of the public key, so a verifier can see which key was used. The stable channel will have a second signature, update.json.sigb (OpenSSH format, made with a hardware key).

What the client checks

  • The signature against the public keys of that channel only. Each channel has two CI keys (a and b), compiled into the client in kog_update_pubkey.h. Trust never depends on the host or on TLS.
  • Rollback protection: sequence higher than the last applied one on that channel, not expired, not from the future, a version of the channel's form, and a version the client rolled back from before is not tried again.
  • Every file's SHA-256 and size before it replaces anything, from allow-listed hosts (github.com/KoG-teeworlds/kog-client/releases/download/ and client.kog.tw).
  • Fail-safe: the previous version stays beside the new one. After 2 starts that did not reach the start screen, the client restores it.

Per-channel keys and rotation

A key of one channel cannot sign another channel, and the channel name is part of the signed text. To replace a CI key without leaving installed clients behind, the client always ships both slots a and b, and the signing secret holds one. A slot is made active only after a client release that contains its public key has been shipped; then the other slot can be replaced. Details: UPDATE_CHANNEL.md.

How to verify a download

Three independent checks. Replace the file name with the one you downloaded. Commands for the checks that need the source are run from a checkout of kog-client.

1. File hash

The start page shows the SHA-256 of each package, read from the signed manifest. Compare it with:

sha256sum KoG-Client-linux.tar.xz
shasum -a 256 KoG-Client-macOS.dmg
Get-FileHash .\KoG-Client-windows.zip -Algorithm SHA256

The three commands are for Linux, macOS and Windows PowerShell, in that order.

2. Build attestation

GitHub keeps a signed statement of which workflow and commit built each file. With the GitHub CLI:

gh attestation verify KoG-Client-linux.tar.xz -R KoG-teeworlds/kog-client

It succeeds only if the file is byte-identical to what the project's workflow built. It tells you where a file came from, not that the code is good.

3. Manifest signature

Check the signature yourself with kogsign, the small verifier the signing job uses:

git clone --depth 1 https://github.com/KoG-teeworlds/kog-client
cd kog-client
cc -O2 -o kogsign scripts/kog/kogsign.c src/engine/external/monocypher/monocypher.c src/engine/external/monocypher/monocypher-ed25519.c -Isrc/engine/external/monocypher
curl -fsSO https://client.kog.tw/canary/update.json
curl -fsSO https://client.kog.tw/canary/update.json.sig
for k in $(python3 scripts/kog/keys_from_header.py ci canary); do ./kogsign verify "$k" update.json update.json.sig; done

Two public keys are tried. One prints ok; the other prints malformed signature file or wrong key id, because the key id in the signature file names the key that signed. If neither prints ok, do not trust the manifest.

Everything in one go (both hosts, signatures, expiry, and the hash of every file in the manifest; needs curl, python3, ssh-keygen and a C compiler):

scripts/kog/verify_published.sh canary

Use dev or stable instead of canary once those channels are published.

The attestation, manifest and verify_published.sh commands were run against the published canary build before this page was written. The hash commands for Windows and Linux and the build commands were not run for it.

The KoG login

Switch: cl_kog_login, on in canary and dev builds, off in stable. The client logs in through your browser (OAuth 2.0 authorization code with PKCE, S256) and then holds a device key pair. Nothing that could be replayed travels over the game connection, and nothing is sent in chat.

  1. The client reads the discovery document of the account server (cl_kog_account_url, default https://kog.tw) and checks that the endpoints are https and on an allowed origin.
  2. It listens on a random loopback port (at most 3 minutes) and opens the authorize URL in your browser, with PKCE and a random state.
  3. You log in on kog.tw. The browser redirects to /callback on the loopback port; the client accepts only the exact path and the right state.
  4. The client exchanges the code and the verifier for a token, reads the account name for the settings, makes an Ed25519 key pair and registers the public half and a device name (POST /api/client/device). Token requests do not follow redirects.
  5. The private key goes into the macOS Keychain or the Windows Credential Manager; on other systems into a file with mode 0600. The access token is discarded.

Log out wipes the private key at once and asks the account server, through the browser, to remove the device. If that fails, the key is gone anyway and the device stays listed on kog.tw until you remove it there.

Join proof Planned: the client can sign a challenge bound to the server address, a nonce, the device and the session, and answers only servers listed for the kog community. The wire format is only a design, so cl_kog_auto_login is off and sends nothing. Documents: LOGIN.md (what is built), the design pull request 238 (join proof) and 229 (the client design). Both are open and not decided.

Network messages

As built, the KoG client defines no new network message types: its protocol definition (datasrc/network.py) has no KoG entry. A design rule is that nothing changes on the wire for 0.7 and stock clients. What is designed but not built:

  • Planned A hello message that announces the client's KoG capabilities to a server (kog_hello).
  • Planned The login proof in the join handshake, so that no credential travels over the game connection (design 238).
  • Planned A KoG master server that hands out server certificates and a revocation list (design 241).
  • Planned A statement about the client build, with a list of known builds and what that can and cannot prove (design 242). A proof about a device key cannot show that the code is unmodified.
  • Planned Opt-in network statistics (kog_telemetry).

The overall design is pull request 229. These pull requests are design documents, and they may change.

Reproducibility

The builds are not reproducible yet. The repository has no documented procedure that rebuilds a release byte for byte, and this has not been tested. What exists instead: public workflows build the files on GitHub, every file carries a build attestation (check 2), releases are immutable, and the signing job verifies attestation, hashes and that the commit is on main before it signs. That shows where a file came from, not that two builds from one commit give identical files.

Build from source

Same as DDNet (see BUILDING.md for the dependencies). The client only, without server and tools, which is how the release workflows build it:

git clone https://github.com/KoG-teeworlds/kog-client
cd kog-client
mkdir build
cd build
cmake .. -DCLIENT=ON -DSERVER=OFF -DTOOLS=OFF -DCMAKE_BUILD_TYPE=Release
cmake --build . --target game-client

The updater is only compiled with -DAUTOUPDATE=ON, and a release build with that option fails while a channel's keys are placeholders. Run the tests with cmake --build . --target run_tests (needs -DDOWNLOAD_GTEST=ON or an installed GTest). A build you make yourself is not on any channel and is not signed.

How releases are signed

  • Canary and dev: a workflow builds from main or dev (never for forks or pull requests), attests the files and makes a draft manifest. A verify job without secrets checks attestations, hashes and the commit; a separate job in a protected environment signs only that manifest with the channel's CI key; publishing commits it to the branch published.
  • Stable Planned: the same, plus a second signature (update.json.sigb) made by the owner on a hardware security key after verifying the release on their own machine. A client requires both, so neither a stolen GitHub account nor a stolen CI secret alone can publish a stable update. There is an emergency stop that signs a halted manifest. The stable keys in the client are still placeholders.
  • Known weak points: the CI private keys are in an encrypted state file of a private repository, so canary and dev testers are exposed if it leaks; with one maintainer, the reviewer of a signing run can approve their own run; and the workflows have had little time in production. The full threat model is in UPDATE_CHANNEL.md.

Security contact

Report vulnerabilities privately through GitHub's vulnerability reporting, not in a public issue. See SECURITY.md. Supported: the latest release, once there is one, and the main branch. This is volunteer work with no response time promised.
