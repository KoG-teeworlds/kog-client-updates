The KoG client is a reference implementation. It exists to demonstrate and test new features that need client integration, such as new network messages and the KoG login. You do not need it to play on KoG: the normal DDNet and Teeworlds clients are fully supported. Builds are for testing and may change or break. Just want to play? →

Updates and trust

Verify a download Built

Three independent checks. Replace the file name with the one you downloaded. Commands for the checks that need the source are run from a checkout of kog-client.

1. File hash #

The start page shows the SHA-256 of each package, read from the signed manifest. Compare it with the output of the command for your system.

Linux:

sha256sum KoG-Client-linux.tar.xz

macOS:

shasum -a 256 KoG-Client-macOS.dmg

Windows PowerShell:

Get-FileHash .\KoG-Client-windows.zip -Algorithm SHA256

If the hash differs, delete the file and download it again. A matching hash only shows that you have the file the manifest names. It does not show that the manifest is genuine: that is what check 3 is for.

2. Build attestation (optional) #

GitHub keeps a signed statement of which workflow and commit built each file. This extra check needs the GitHub CLI, which the other checks do not:

gh attestation verify KoG-Client-linux.tar.xz -R KoG-teeworlds/kog-client

It succeeds only if the file is byte-identical to what the project's workflow built. It tells you where a file came from, not that the code is good.

3. Manifest signature #

Check the signature yourself with kogsign, the small verifier the signing job uses. It is built from a few files of the repository, with Monocypher for Ed25519:

git clone --depth 1 https://github.com/KoG-teeworlds/kog-client
cd kog-client
cc -O2 -o kogsign scripts/kog/kogsign.c src/engine/external/monocypher/monocypher.c src/engine/external/monocypher/monocypher-ed25519.c -Isrc/engine/external/monocypher
curl -fsSO https://client.kog.tw/canary/update.json
curl -fsSO https://client.kog.tw/canary/update.json.sig
for k in $(python3 scripts/kog/keys_from_header.py ci canary); do ./kogsign verify "$k" update.json update.json.sig; done

Two public keys are tried. One prints ok; the other prints malformed signature file or wrong key id, because the key id in the signature file names the key that signed. If neither prints ok, do not trust the manifest.

The keys come from the client's own header, src/engine/client/kog_update_pubkey.h: the same keys the client has built in. Read how a manifest is built on the update channel page.

Everything in one go #

Both hosts, signatures, expiry, and the hash of every file in the manifest. It needs curl, python3, ssh-keygen and a C compiler:

scripts/kog/verify_published.sh canary

Use dev or stable instead of canary once those channels are published.

What was run. The attestation, manifest and verify_published.sh commands were run against the published canary build before the previous version of this page was written. The hash commands for Windows and Linux and the build commands were not run for it. These pages were reorganised afterwards, and the commands were not run again.

Warning. None of these checks proves that a build is free of bugs or of unwanted behaviour. They show who built the file, from which commit, and that it was not changed on the way to you. Builds are not code-signed for Windows or macOS yet, which is why those systems warn when you start them.
